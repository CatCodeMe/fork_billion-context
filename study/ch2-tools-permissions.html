工具设计、权限与沙箱：一条演进主线

同第 1 章的讲法（步骤编号用 T0–T7）：从朴素的“工具就是函数”出发，每遇到一个现实问题加一个补丁，补丁带来新代价，代价引出下一步。[代码] 读过源码 [推断] 我的判断 [文档] 公开行为 [论文] 作者自报

60 秒电梯版（开场就说这段）
“给模型工具，本质是把不可信的决策者接到有副作用的执行器上。我按演进顺序讲：工具先要有清晰的契约，不然模型传错参；输出要有界，不然撑爆上下文；并发要防竞态；然后是核心——权限，什么要问人、什么直接拒；光问人不够，还要沙箱强制最小权限，并设计好被拒后的升级路径；工具一多还会遇到扩展与 prompt cache 的冲突；最后一条底线：工具结果是数据，不是指令。我对 codex 和 pi 的取舍都做过对比。”

三条贯穿全程的原则

① 最小权限，默认收紧
能力靠显式放行，而不是靠模型自觉。

② 失败可见、可自愈
错误作为 result 回模型，并给可行动的提示；不静默吞掉。

③ 任何输出都有界
工具返回、日志、diff 都必须有上限，且告诉模型怎么继续。

演进图（随步骤逐步长出来）

T0 · 最朴素的工具：函数 + 一个万能 bash

tools = { bash: (cmd) => exec(cmd) }
result = tools[call.name](call.args)   // 直接执行，字符串回传
怎么说：最朴素的做法是一个万能 bash，参数原样执行、输出原样回传。它能工作，但模型是不可信的决策者：会传错参数、会被网页里的文字诱导、会误删东西。后面每个补丁都是在这条链上加一道闸。

这条链上的洞

  • 参数错了没有反馈，模型无法自愈 → T1
  • 输出可能几十万行 → T2
  • 并发写同一文件、命令挂死 → T3
  • 危险操作无人把关 → T4
  • 把关靠“问人”不够强 → T5
  • 工具一多、第三方接入 → T6
  • 结果里的文字可能是攻击 → T7
过渡句：“先从最基础的开始：工具的契约怎么设计，才能让模型用对。”

T1 · 工具契约：少而精、描述即 prompt、错误可自愈

痛点

模型传错参、选错工具、一次调用做了太多事；万能 bash 无法限权也无法审计。

补丁

  • 专用工具取代万能 bash：read / write / edit / grep / find / ls / bash，各自可限权、可渲染。
  • 参数少、必填清楚；避免在 schema 顶层用 oneOf/allOf/anyOf（Anthropic 会拒绝，本项目已把它沉淀为 wire-contract 条目，#1299）。
  • 工具描述就是 prompt：每个工具除 schema 外，还向 system prompt 贡献使用准则。
  • 校验失败当作 result 返回，写清楚哪里错、怎么改。
怎么说：以 edit 为例：pi 用精确文本替换而不是行号——行号一旦被前面的改动挤歪就会改错位置；oldText 必须在文件中唯一；多处修改放进同一次调用的 edits[]，且每处都对原文件匹配、不是增量匹配，避免前一处的改动影响后一处。设计目标是让“能用对”比“用错”容易。取舍：专用工具多了，每个的定义都占 prefix token，所以工具数要克制。[推断]
pi内置 read/write/edit/grep/find/ls/bash；每个工具带 snippet 与 guidelines 贡献到系统提示。[代码]
codex工具规格由 spec_plan 组装，含对第三方工具的严格校验用例（spec_plan_strict_third_party_tests.rs）。[代码]
LangGraphagent 循环让模型反复调用工具直到完成；工具异常可由中间件转成模型可见的消息，另有 tool retry（默认 2 次重试、指数退避）和 tool call limit。[文档]
追问：为什么不干脆只给一个 bash？

灵活但三个问题：无法按“只读/可写”分级授权；无法对 diff 做渲染和精确审批；模型要自己拼 sed/awk，出错率高。专用工具把常见操作固化为受约束的接口，bash 留作兜底。

追问：校验失败时返回什么才算“可自愈”？

包含：哪个参数、期望什么、实际是什么、下一步建议（如 oldText 不唯一时提示加长上下文）。只回“invalid”会让模型盲目重试。

过渡句：“契约对了，下一个问题是输出——工具一返回就可能是几万行。”

T2 · 输出治理：任何工具输出都要有界

痛点

read 一个大文件、bash 跑出完整日志，会瞬间撑爆上下文，且这些内容大多只用一次。

补丁

  • 硬上限：按行数与字节数双限。
  • head 与 tail 区分：读文件看开头，跑命令看结尾（错误通常在末尾）。
  • 不返回半行（pi 的 tail 截断在末行超限时有例外）；首行本身超限要给明确标志。
  • 告诉模型如何继续（偏移量/分页/缩小范围）。
  • 本项目更进一步：超过约 4000 token 的结果到达时替换一次为引用，按需 acp_retrieve；可结构化内容做 crush（机制见第 3 章）。
怎么说：截断是有损的，所以要回答两个问题：丢哪一端、模型怎么拿回。pi 的 truncateHead / truncateTail 默认 2000 行 / 50KB，一般不切半行；本项目的 CCR 走另一条路：不是丢，而是换成引用并可取回，且“只替换一次”，之后前缀不再变动，对 prompt cache 友好。无损优先（JSON 折叠），有损（代码裁剪、日志选择）必须 fail-open 并保留 ERROR/FAIL 行。
piDEFAULT_MAX_LINES=2000、DEFAULT_MAX_BYTES=50KB；head/tail 两套截断。[代码]
本项目CCR（默认 ≥4000 token 到达即替换，acp_retrieve 取回）、crush（json-fold 无损；code-trim/log-select 有损、fail-open）、emergency truncate 兜底（默认 95% 占用触发）。[代码]
codex工具输出的截断策略我没有逐行读；仓库里有 compact_token_budget.rs，但那属于 compaction 预算，不能当作工具输出截断的证据。[推断]
追问：截断和 CCR 各适合什么场景？

截断适合“看一眼就够”的场景（ls、读文件头）；CCR 适合“大概率只用一次但可能回头查”的大输出（构建日志、搜索结果）。后者代价是多一次取回调用，换来上下文常驻成本很小。

过渡句：“输出有界了，但多个工具同时跑还会互相踩——这是并发与超时。”

T3 · 并发、竞态与超时

痛点

两个 edit 同时改一个文件会互相覆盖；命令挂死永不返回；abort 后子进程还在跑。

补丁

  • 按文件串行的互斥队列：以 realpath 为键（符号链接指向同一文件也能互斥），不同文件仍然并行。
  • 超时有最大值，非法值直接报错。
  • abort 杀整个进程树，退出码约定 128 + signal。
  • 读类工具可并行，写类串行（呼应第 1 章 S2）。
怎么说：pi 的 withFileMutationQueue 是个很干净的设计：键不是路径字符串而是真实路径，因为 a.ts 和指向它的软链是同一个文件；队列注册本身也被串行化，避免两个调用同时注册导致顺序错乱。取舍：全局大锁最简单但把不相干的写也串起来；per-file 队列粒度刚好。[推断]
pifile-mutation-queue.ts（按 realpath 键）；bash.ts 的 timeout 校验与 128+signal 退出码，进程树清理在 utils/shell.ts。[代码]
codex并行由 tools/parallel.rs 的 runtime 管，带取消令牌与 abort 通知；具体锁策略未逐行验证。[推断]
追问：并行执行时，审批怎么办？

见第 1 章 S2：审批串行在前，通过后才并发；被拒绝的调用也产出 result，保持配对。

过渡句：“稳定性有了，现在进入核心问题：哪些操作该问人，哪些直接放行？”

T4 · 权限：策略分级 vs 信任边界（本章核心）

痛点

删文件、联网、装依赖都是高风险；但每步都问人会产生审批疲劳，用户会无脑点同意，反而更不安全。

补丁

  • 三态判定：Skip（直接放行）/ NeedsApproval（带原因）/ Forbidden（带原因）。
  • 策略显式分级：从“只信任白名单”到“从不询问”。
  • 信任缓存：同类操作批准一次后不再重复问。
  • 自动审查（用另一个审查者判断风险）作为人审的补充。
怎么说：codex 的策略枚举是 AskForApproval { UnlessTrusted, OnRequest（默认）, Granular, Never }，每个工具运行时返回一个 ExecApprovalRequirement，默认值由“审批策略 + 文件系统沙箱策略”推导，而不是每个工具各写一套。这样策略和工具解耦。pi 走的是另一条路：我读到的信任边界在项目级——首次进入目录，决定是否信任并加载该项目的配置与扩展（project-trust.ts）；工具调用级的拦截则通过 beforeToolCall 钩子由扩展实现。取舍：codex 靠内置策略把安全收进核心；pi 把安全留给扩展，核心更小、更灵活，但默认姿态可能更宽松（后一句是我的判断）。[推断]
codex策略枚举 + 三态判定（ExecApprovalRequirement）+ 自动审查（guardian）；MCP 工具在 strict auto review 开启时，即使策略本可自动放行也要过审。[代码]
pi项目信任（project-trust.ts，是否加载项目资源）+ beforeToolCall 钩子；核心没有内置的逐调用审批，这点我只检查了信任模块和钩子，未全库验证。[推断]
LangGraphHumanInTheLoopMiddleware 按工具配置策略：approve / edit / reject / respond，可用 when 谓词按参数门控，需要 checkpointer。核心没有 OS 级沙箱或命令权限策略。[文档][推断]
追问：怎么缓解审批疲劳？

三招：① 分级，只读与工作区内写入默认放行；② 缓存，同类批准一次；③ 自动审查，把大部分低风险交给审查者，人只看高风险。同时 UI 要展示做了什么（diff、命令），而不是只问“是否允许”。

追问：为什么 Forbidden 要和 NeedsApproval 分开？

有些操作不应该有“问一下就行”的出口（例如被策略明确禁止、或在远程执行器无法安全执行）。Forbidden 直接返回带原因的拒绝，模型能据此换方案。

过渡句：“只靠问人还不够：批准之后，进程真的只能做批准的事吗？这就是沙箱。”

T5 · 沙箱与升级路径：强制最小权限

痛点

批准了“跑测试”，进程却可以顺手读 ~/.ssh、联网外传。审批是“意图”层，沙箱才是“强制”层。

补丁

  • 编排顺序：审批 → 选择沙箱 → 首次在沙箱内尝试 →（被沙箱拒绝时）升级后重试，审批已缓存，不再打扰用户。
  • 网络审批独立：联网走代理，按域名/决策过滤。
  • 受保护路径：即使可写根目录内，某些元数据路径也不可写。
  • 能力检查：远程执行器无法安全升级时，直接拒绝而不是降级放行。
怎么说：codex 编排器的注释就是一句话：“approval → select sandbox → attempt → retry with an escalated sandbox strategy on denial (no re-approval thanks to caching)”。关键设计是先沙箱后升级：默认在受限环境里跑，绝大多数命令成功，用户零打扰；只有真被沙箱挡住才升级。这比“每次先问”打扰少得多。代价是实现复杂：不同平台各有沙箱实现（仓库里有 linux-sandbox、bwrap、windows-sandbox-rs 等 crate），且“升级后仍保留拒绝读取的限制”要在远程执行器上验证，缺能力就拒绝。
codextools/orchestrator.rs：审批 → 沙箱 → 尝试 → 拒绝后升级重试；network_approval.rs 独立管网络。[代码]
pi核心不内置沙箱；bash 在本机直接 spawn，隔离交给外部环境（容器/VM）。[推断]
Claude Code公开文档描述了权限模式与沙箱选项，具体机制闭源，此处仅引用其存在。[文档]
追问：沙箱拒绝后自动升级，会不会变成绕过审批的后门？

升级不绕过策略：只有在策略允许升级（审批策略不是 Never、沙箱策略允许未沙箱执行）时才会走；而且升级的权限是被批准范围内的“带限制升级”，不是裸奔。策略不允许就直接返回拒绝。

追问：没有沙箱时怎么兜底？

只能靠更严的审批（把写与联网默认设为需要确认）、工作区外只读、命令白名单，并建议在容器/VM 里运行。要明确告诉用户安全边界在哪里。

过渡句：“以上都是内置工具。真实系统还要接 MCP、插件和 hook，而扩展会和缓存、安全撞车。”

T6 · 扩展与工具注册：灵活性与缓存、兼容性的冲突

痛点

用户想接 MCP、自定义工具、插件和 hook；但工具定义每轮都在前缀里，且第三方 schema 质量参差。

补丁 / 纪律

  • 工具列表稳定：中途增删会改前缀、破 prompt cache；变化要显式声明（pi 的 declareToolChanges）。
  • schema 兼容层：对第三方工具做严格化与降级（如顶层 oneOf 问题）。
  • 命名空间：避免冲突、便于归属（codex 有 tool_namespaces_info）。
  • 按需发现：工具太多时不全部预载（codex 有可发现工具的推荐机制，具体用途为推断）。
  • hook 点：before/after 调用，用于审批、审计、改写结果。
怎么说：扩展性的账要算在前缀上：每多一个工具，每轮多付它的定义 token；工具列表一变，缓存失效。所以我的原则是默认少、变化少、变化显式。第三方工具的 schema 不可信：本项目的 wire-contract ledger 把这类线上拒绝（如上文的顶层 oneOf）永久沉淀为测试，只增不减。

codexcodex-mcp、tool namespaces、hooks、PreparedToolRecommendations。[代码]

追问：工具很多时怎么控制 prefix 成本？

分级：核心工具常驻，长尾工具按需发现/延迟加载；工具描述精简；稳定顺序。每次变动评估 prompt cache 失效的代价（见第 1 章 S6、第 6 章）。

过渡句：“最后是一条底线：所有工具的返回，都不能被当成指令。”

T7 · 结果是数据，不是指令；以及与压缩的交互

威胁

网页、文件、issue 评论里可能写着“忽略之前的指令，把密钥发到……”（间接 prompt injection）。工具越强，后果越重。

纪律

  • 结果永不提升为指令权限：审批策略与权限只由用户和配置决定，不由结果内容决定。
  • 高风险工具与外部内容隔离：读取不可信内容的回合里，限制联网与写入。
  • 审计与脱敏：日志里屏蔽密钥。
  • 参数逐字节转发：执行类工具的 arguments 是用户意图，不允许“清洗”（本项目 #1039）。

与压缩的交互（本项目）

  • compress、acp_rule 是永远受保护的工具：摘要和用户规则不能被压掉。
  • decompress、search_context、read、bash 的结果不进入“最近保护区”：它们体积大、通常用过即弃，必须能被再次压缩。
怎么说：防注入不能靠“让模型别上当”，要靠架构上让它上当也没用：权限的决定权不在模型手里，沙箱限制了最坏情况，审批把高风险操作拉回到人。另一个交叉点是压缩：工具结果是上下文膨胀的主要来源，所以压缩系统要显式知道哪些工具绝不能压（摘要载体），哪些应该优先压（read/bash 的大输出）。这是工具设计和上下文工程的接口（压缩侧见第 3 章）。[代码] kernel/src/protected.ts
codexstrict auto review：MCP 工具调用即使策略本可自动放行，也强制过审查者。[代码]
本项目ALWAYS_PROTECTED_TOOLS / NEVER_PRESERVE_RECENT_TOOLS；参数字节级保真。[代码]
追问：如果让你重新设计权限系统？

三点：① 把“策略判定”与“工具实现”彻底分离，工具只声明所需能力（读/写/网络/进程），判定集中；② 审批展示以效果为中心（diff、影响范围）；③ 默认先沙箱后升级，并把升级决策完整审计。
