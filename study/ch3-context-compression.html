上下文工程与压缩：一条演进主线

本仓库的核心。同前两章的讲法：从最朴素的“全量发送”出发，遇到问题加补丁，补丁带来新代价，代价引出下一步。[代码] 读过源码 [推断] 我的判断 [文档] 公开行为 [论文] 作者自报

60 秒电梯版（开场就说这段）
“上下文压缩本质是在信息保真、缓存稳定、成本三者之间做取舍。我按演进顺序讲：朴素的全量发送会越滚越贵；滑窗会丢目标和破坏缓存；改成摘要又会信息衰减，所以要可回溯；一次重写太大，于是分层折叠让多数改动只发生在最近一层；什么时候压由增长量驱动，并让正在干活的模型自己写摘要；大输出前置治理；代理不拥有对话，所以要有身份与对账；每一层都有更粗但更可靠的兜底；最后诚实说明证据强度。”

三条贯穿全程的不变量

① 有损但不丢
折叠只是换一种视图，原文保留，需要时可取回。

② 前缀稳定
只追加、少改写，才能命中 prompt cache。

③ 身份不漂移
消息 id 与引用号永不复用，对账失败要可解释。

演进图（随步骤逐步长出来）

K0 · 最朴素：每轮全量发送

怎么说：最朴素的做法是每轮把完整 history 发给模型。它正确，但有两个问题：总开销随轮数二次增长（第 n 轮要重发前 n−1 轮），以及迟早超出窗口。缓存能缓解重复付费，但解决不了窗口上限。后面的每一步都是在回答：“怎么让发出去的东西变小，又不伤任务”。

这个朴素版的洞

  • 窗口满了怎么办 → K1
  • 丢东西会伤任务，怎么保真 → K2/K3
  • 改写会破坏缓存 → K4
  • 什么时候压、谁来压 → K5
  • 大工具输出占大头 → K6
  • 代理拿到的历史会被客户端改写 → K7
  • 压缩失败了怎么办 → K8
过渡句：“最直觉的办法是把最老的丢掉，看看它有什么问题。”

K1 · 滑窗/截断：丢最旧的

痛点

  • 丢掉的往往是任务目标和约束（一开始用户说的话）。
  • 可能把 tool_call 和 tool_result 拆开，provider 直接拒绝。
  • 每轮丢一点，前缀每轮都在变，prompt cache 几乎全废（缓存经济见第 6 章）。

能打的补丁

  • 固定首条用户消息不被丢（本项目 kernel 对首条用户消息无条件保留，且还因为部分后端要求会话必须以 user 开头，DESIGN §8.1）。
  • 切点避开 tool result，保证配对。
怎么说：滑窗最大的问题不是丢信息，而是丢了就没了，并且每轮都改前缀。所以结论是：要压，就必须把被压掉的内容换成等价的更短表示，而且改动要集中、稳定。
过渡句：“更短的等价表示，最自然的就是摘要。”

K2 · 摘要折叠：把一段前缀换成摘要

痛点

摘要要有人写；写摘要是个有损操作；什么时候压、压哪一段也要决策。

补丁

  • 谁来写摘要：专起一次摘要请求，或让正在工作的模型自己通过工具写。
  • kernel 的分工：模型写摘要，kernel 决定何时、压哪段、落状态、渲染；它是不调模型的纯函数库，摘要作为字符串入参。
  • 范围与长度约束：默认最小压缩范围 5000 token，摘要长度 50–20000 字符。
  • 保留近期：默认保护最近 5 条消息 / 约 5000 token。
怎么说：让正在干活的模型自己写摘要有两个好处：它拥有最完整的当下上下文，知道什么值得保留；也省掉一次额外请求。代价是依赖模型配合，所以后面要有触发和兜底。kernel 做成无状态、不做 I/O 的纯库，是为了让同一套逻辑能被代理、插件、不同宿主复用。
pi压缩时专门发起摘要请求；保留近期 keepRecentTokens=20000，切点不落在 tool result 上。[代码]
codex本地压缩（compact.rs）或远端压缩（compact_remote_v2）；摘要带固定前缀模板。[代码]
本项目模型通过 compress 工具给摘要；kernel 不调模型；默认配置见 kernel/src/config.ts。[代码]
追问：摘要写差了怎么办？

不能指望每次都写好，所以设计成可回溯（下一步）：摘要差，模型可以 decompress 回到原文。另外高层提示词里要求摘要保留关键标识（路径、命令、结论）。

过渡句：“但摘要是有损的，如果原文被丢掉，就回不去了——所以关键是让它可回溯。”

K3 · 可回溯：有损视图，无损存储

痛点

摘要会漏掉后来才发现重要的细节；摘要的摘要会逐层衰减。

补丁

  • 折叠不删除原文：块存储里同时保留原文与摘要，渲染视图只显示摘要。
  • 引用标签：摘要里用 mNNNNN 引用原消息，模型可 decompress 还原，或 search_context 检索。
  • 取回的内容可再次被压缩：decompress、search_context、read、bash 的结果不进入“最近保护区”，避免取回后上下文变得不可回收。
  • compress 调用本身受保护：compress 与 acp_rule 永远不被压掉，否则摘要和用户规则会丢。
怎么说：我把它概括为“有损视图，无损存储”：模型看到的是短的，但信息没有真正丢。这样摘要质量不再是单点风险，最坏情况是多一次取回。代价是要维护块存储和引用关系，并且引用号必须永不复用（K7）。
pi / codex压缩后旧消息仍在会话记录里（用于展示与恢复），但模型看到的只有摘要；模型侧没有“按引用取回原文”的工具。[推断]
本项目kernel/src/decompress.ts、ccr.ts（acp_retrieve）、protected.ts。[代码]
过渡句：“可回溯解决了保真，但每次折叠一大段，仍然会让缓存失效——所以要控制改动落在哪。”

K4 · 分层折叠 T1/T2/T3：让改动集中在最近一层

痛点

每次都重写整段前缀，会让后面全部缓存失效；而且反复“摘要的摘要”会衰减。

补丁（类似 LSM tree）

  • T1：新近、小块摘要；T2：多个 T1 合并后的更概括的块；T3：更老更概括。
  • 大多数折叠只产生新的 T1，老层字节保持稳定。
  • 升层看token 质量：待蒸馏质量超过步长的 1.5 倍（tier2GrowthMultiplier，即 75K），且大于低层的有效待压量，才选 T2/T3。数量触发（tier2Trigger/tier3Trigger）默认 1000 / 2000，等于关闭，只有显式配置才生效（#379：块数不是需求信号）。[代码]
  • 首条用户消息固定在直接范围，折叠锚点不早于它（#2733）。
怎么说：LSM 的类比很贴切：写入先落到小而新的层，老数据很少被重写。放到缓存语境里就是——前缀越靠前越稳定，折叠的“写放大”集中在尾部。取舍是复杂度：要管理多层块、升层时机，以及客户端回传历史与内部块的对账（K7）。
核对：文档和代码有出入吗？

有。kernel/DESIGN.md 的管线描述里有 merge-blocks 节点，但 buildNodes 的实际节点表里没有它。面试时讲“分层”以代码为准，可以主动说“设计文档比代码超前”。[代码]

过渡句：“有了分层，下一个问题是：什么时候触发一次折叠？”

K5 · 触发：增长驱动 + 模型自己压（nudge）

痛点

按占用率触发会在“快满时”才行动；按轮数触发又和实际成本无关；模型也未必愿意压。

补丁

  • 固定增长步长 50K：growthFloor = growthCap = 50000，不随窗口缩放（设计决定，AGENTS.md KDD#8）。
  • 增长门：距上次提示的增长至少 max(20K, 0.45×50K)=22.5K 才提示，避免微小增长就触发。
  • 高压带：占用 ≥75% 时绕过增长门与节奏，只要有足够可压量就提示；紧急：≥95% 触发确定性截断（K8）。占用低于 45% 不提示。
  • 最小收益门（高压带）：可压量至少 max(5000, 窗口的 1%) token。
  • 用户逃生口：compress.nudgeGrowthTokens 可把步长调大（想更懒的用户）。
怎么说：为什么不用窗口比例？团队明确决定“增长驱动，不要用占用率/数量做代理指标”：1M 窗口的会话每涨 50K 就折叠一次是想要的精简行为，而不是等快满才处理。代价是压缩更频繁，但每次折叠范围小、前缀更短、成本更低。提示（nudge）是软触发，由模型决定是否、如何压；这比硬编码规则更能保留“值得留”的信息。
picontextTokens > window − reserveTokens(16384) 触发，属阈值型。[代码]
codex回合前预检 + 回合中 should_roll_over 触发 MidTurn 压缩，也属阈值型。[代码]
本项目增长驱动的 decideNudge；T2/T3 升层按步长倍数与待压量仲裁。[代码]
追问：如果模型就是不压怎么办？

提示分级：普通 nudge → 高压带更强的提示 → 紧急区的确定性截断（K8）。也就是不把可靠性押在模型配合上。

过渡句：“触发解决了‘何时’，但上下文里最大头往往是工具输出——要在进入折叠之前先处理它。”

K6 · 前置治理：大工具输出先换成引用

痛点

read、bash 的大输出是上下文膨胀主源，且多数只用一次。

补丁

  • CCR（replace-once-at-arrival）：到达时一次性替换为引用，阈值约 4000 token，按需 acp_retrieve 取回；只替换一次，之后前缀不再变。
  • crush：JSON 折叠无损；代码裁剪、日志选择有损且 fail-open，保留 ERROR/FAIL 行。
  • CCR 与 crush 在 kernel 默认配置里都是 enabled: false；bili 侧 CCR 同样是 opt-in（compress.ccr.enabled，且需有取回工具通道，插件模式下不启用）。[代码]
怎么说：先治理再折叠有两个好处：折叠要处理的量变少，并且大块内容不会在多次折叠里被反复搬运。（输出治理细节见第 2 章。）
展开：kernel 每轮管线的节点顺序 [代码]

reconcile-live-ids → assign-refs → sync-blocks → prune → ccr-store → absorb-hide → crush → absorb-prompt（这三个节点按配置自行开关）→ filter → hide-compress-calls → recommend → nudge-inject → emergency-truncate → render-refs

过渡句：“前面都假设代理能稳定地看到‘同一份历史’，但客户端会改写它——这就是身份与对账。”

K7 · 身份与对账：代理不拥有对话的代价

痛点

代理每轮拿到的是客户端回传的历史，它可能被编辑、重发、被客户端自己压缩；内部块要和它对得上，否则折叠会错位，甚至把摘要挂在错的消息上。

补丁

  • content-hash id 标识消息；引用号 mNNNNN 永不复用：摘要会跨很多轮引用它，号码一旦被重新分配，解压缩会静默指向错误内容。
  • 多级对账（reconcile ladder）：后缀/前缀锚点、toolCallId、归一化文本、位置匹配、助手回合键、图片变体，最后回收“僵尸块”。
  • 前缀亲和（hash 链）：用于把请求归到正确的会话/分叉。[推断]
怎么说：这是代理模式的长期成本：pi 和 codex 自己持有 history，所以不存在这个问题。本项目把它做成显式的一层，并把“号码永不复用”写成 kernel 的硬契约，因为这类错误没有报错、只有错答案。如果用插件模式（客户端拥有对话），状态天然一致，这层负担会小得多。
pi / codex自己持有并追加 history，没有“回传历史对账”这一层。[推断]
本项目src/fold-reconcile.ts、src/prefix-affinity.ts、AGENTS.md「Kernel Contract: Message Ids Are Never Reused」。[代码]
追问：对账失败时怎么办？

退化而不是错放：对不上就不应用该次折叠（保持原文发送），并记录可观测的日志；宁可多花一些 token，也不让摘要挂错位置。[推断]

过渡句：“最后一类问题：如果上面任何一环失败，系统怎么不崩？”

K8 · 兜底阶梯：每一层都有更粗但更可靠的下一层

痛点

模型可能不配合；摘要可能失败；窗口可能在一次大输出后瞬间逼近上限。

阶梯

  1. nudge（软提示，模型自己压）；
  2. 高压带（≥75%，加强提示）；
  3. emergency truncate（≥95%）：对旧的大 tool result 保留头尾各 2000 字符、中间换成标记，按体积从大到小，直到降到约 85.5%（0.95×0.9）；最近 preserveRecentMessages（默认 5）条不动；tool result 不够才碰 user/assistant 文本，且从不碰已渲染的摘要块；
  4. preflight（宿主侧 src/preflight.ts，#247）：输入本身超过窗口时，发起专门的摘要调用从最旧范围开始折叠；仅当溢出倍数大到 LLM 折叠不可能收敛（#2383）才改用确定性 digest；
  5. terminalEscape：用完截断仍无法降到限制以下、连续 3 次（terminalEscapeAfter）后发出信号，由宿主提示“新开会话或用原生 compaction”，避免无声卡死。
怎么说：设计原则是优雅降级：越往后越粗暴、越不依赖模型，但越可靠；而且每一层都 fail-open，宁可少压也不让请求失败。可观测性也是兜底的一部分：截断候选为 0 时要告警，否则会出现“静默不生效”（#300）。
过渡句：“说了这么多机制，最后要回答：效果到底有多少证据？”

K9 · 证据与改进：诚实说明强度

论文里的数字，按来源分开讲

生产观察（三个宿主、单用户、非随机）

  • 常驻宏观折叠约 70×；
  • 调用间隔不足 2 分钟时缓存读占比 94.2%（该间隔占约 89% 流量；缓存读占比随间隔变长单调衰减，>60 分钟仅 9.1%）。

对照 pilot（单一模型 qwen3.8-27b，temperature 0，本地 sglang，Session Marathon 18 个串行任务）

  • 压缩臂相对 sliding 基线，计费 token 降低 31–54%（默认 −31.5%，extreme −53.7%）；
  • 重新读取次数少 2.7 倍（−63%），但论文把它归因于“提示词准则 + 引用标签”这一整体，而不是压缩本身（128K 窗口下压缩从未触发的单次对照里已出现 −62%）。

论文自己写明的局限：单用户、观察性无随机对照、受控臂只用一个模型（温度 0）、摘要质量在 RQ2 前未量化。[论文]

我会怎么补

  • A/B：固定任务集，比较有/无压缩的成功率、轮数、重新读取次数、成本。
  • 摘要质量评估：压缩后让模型回答早期细节问题（回读测试）。
  • 对账可观测：对账成功率与回退次数作为一等指标。
怎么说：我会先说结论：机制层面的正确性有测试证据（契约、e2e、不变量），效果层面分两类：生产观察，以及单一模型上的对照 pilot；两者都是作者自报，后者的 2.7× 还要归因到提示词与引用标签整体。然后给出补法。把“证据强度”讲清楚，比把数字讲得漂亮更像专家。

如果重做，改这四点

  1. 用实测 usage 校准 token 估算（触发只做预判）。
  2. 文档与代码对齐（如 merge-blocks）。
  3. 把对账层做成可观测、可回放。
  4. 能走插件模式就走插件模式，代理模式只留给没有扩展点的客户端。
