第 2 章 · 状态正确性

消息身份：折叠状态靠什么认出"同一条消息"

折叠状态记录的是"哪些消息被哪个块覆盖"。如果客户端下一次重放时消息的身份变了，覆盖就失效，原文会重新涌回线上，摘要却还在。这一章是整个系统最容易出事、也最能体现工程判断的地方。

基本机制 代码

  • 消息身份由内容哈希给出：role、contentType、toolCallId、toolName、text 一起参与，重复内容再加簇后缀。
  • 再给每条消息分配稳定短号 m00001…，模型靠它引用范围。assign-refs 是 ref 表唯一的写入者。
  • ref 永不复用。摘要会引用旧编号，复用会让 decompress 静默指向别的消息。游标是 已用最大值 + 1，所以宿主不能收缩 ref 表。
  • 含无法恢复媒体（只有远程 URL、无字节）的消息得到 BLOCKED ref：不展示、不折叠，因为折叠等于永久销毁。

模拟器：客户端改了历史，对账会怎么处理？

选一种现实里出现过的漂移场景，看哪一层认领它，或者为什么选择不认领。核心取舍：只在有协议级唯一证据或完整规整文本相等时认领，不做模糊相似，因为误归属比漏匹配代价高。

第 4 章 · 上下文预算管理

何时压缩：增长门控的 nudge

内核不自己压缩，它只决定"这一轮要不要提醒模型去压"。判断依据是需求侧信号：自上次以来涨了多少、有多少内容已经可以回收，而不是单纯的填充率。

模拟器：这一轮会不会发 nudge？

按 decideNudge 的分支复刻（高压带、增长门、首见质量绕过、T1/T2/T3 仲裁、最小收益门）。省略了分层节奏的 cadence 记账。拖动滑块，看哪一道门拦住了它。

第 6 章 · 请求组装

视图稳定性：摘要放哪里，决定缓存是否存活

prefix cache 对"字节前缀"敏感，一个字节变了，后面全部失效。所以重建视图时，每条摘要的位置、措辞、角色都要稳定。这一章是 prune 里最费心思的部分，也是仓库里 #2733 这类修复的来源。

第 7 章 · 上下文预算管理

工具输出治理：先别让大块进来，再谈压缩

会话里体积最大的是工具输出，价值密度却最低。除了模型驱动的折叠，系统还有几条更便宜、更确定的减重路径。它们的共同约束是：同一条消息每轮的字节必须一致，否则缓存抖动。

模拟器：一个工具结果会经过哪些处理？

选内容类型和体积，看到达时、之后每一轮、以及高压时分别发生什么。可开关 crush（默认关）。

    手段有损？可逆？何时发生对缓存
    CCR 入库否acp_retrieve 取回原文到达时一次replace-once，之后字节不变
    crush json-fold否（构造上无损）可还原每轮纯函数输入同则输出同
    crush code-trim / log-select是否，但保留所有 ERROR/FAIL 行每轮纯函数与 query 无关，故稳定
    absorb是（模型蒸馏）否超阈值时强制落块后稳定
    模型折叠 compress是decompress 恢复nudge 之后改写折叠点之后的字节
    emergency-truncate是否使用率 ≥95%必然破坏，是最后保险

    第 8 章 · 协议与可靠性

    协议与可靠性：永远不要发会 400 的请求

    一个压缩系统一旦出错，代价不是"压得不好"，而是整个会话永久不可用。仓库里数百个带编号的修复，绝大多数都落在这一章的几个主题里。

    疏，不是堵。AGENTS.md 把它写成第一原则：修复要消除产生缺陷的机制，而不是在传输途中改写载荷来隐藏症状。典型反例是 #933 到 #1039：为了不让回显标签漏进 TUI 去过滤工具调用参数，结果静默破坏了用户真实写入的内容。

    必须诚实面对的局限 论文

    • 证据是单用户、观察性数据，没有随机对照；反事实节省部分来自建模。
