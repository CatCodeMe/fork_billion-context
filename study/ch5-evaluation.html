评估：怎么证明一个压缩代理“对”且“有效”

同前几章的讲法：从“手点几轮看看”出发，遇到问题加补丁，补丁带来新代价，代价引出下一步。核心区分：机制正确性（可以确定性证明）与效果有效性（只能统计性论证）。[代码] 读过源码 [推断] 我的判断 [文档] 公开行为 [论文] 作者自报

60 秒电梯版（开场就说这段）
“评估要分两类问题。机制正确：压缩后会不会改坏字节、复用 id、被上游 400 拒绝——这类是确定性的，所以用不变量测试、契约/golden、字节级 prover、fuzz、甚至 Z3 定理去钉死，而且每次线上事故都变成只增不减的回归账本。真实行为：mock 测不出真实客户端的 UA、重试和 wire 怪癖，所以有真实客户端 e2e，但它贵，所以默认关、只在改请求管线时跑，CI 按路径分层触发。效果有效：能省多少、会不会丢信息，这要靠对照实验——固定任务集、多臂、带召回探针，并且归因要拆。最后一条原则：证据强度要如实标注，生产观察和受控试点不是一回事，作者自报也不是第三方复现。”

三条贯穿全程的不变量

① 能证明的别靠看
确定性性质（字节稳定、id 不复用）用测试甚至定理，不用目测。

② 事故变账本
每个线上拒绝或事故都变成永久用例，账本只增不减。

③ 证据要分级
机制证明、受控试点、生产观察，强度不同，报告时分开说。

演进图（随步骤逐步长出来）

E0 · 最朴素：手点几轮，感觉没问题

怎么说：最朴素的评估是自己用一阵、看看有没有出错。对普通应用够用，对压缩代理不行，因为它的失败模式有三个特点：静默（引用号被复用，没有报错只有错答案）、低频（只在某家上游的某种 wire 形态下才 400）、昂贵（缓存被悄悄打断，只体现在账单上）。这些都不是“用着觉得卡”能发现的。所以我把评估拆成两类问题，各用不同工具。

这个朴素版的洞

  • 确定性性质（字节稳定、id 不复用）→ E1–E3
  • 真实客户端的行为 mock 不出来 → E4
  • 测试太多太贵，怎么跑 → E5
  • agent 的评估看结果还是看过程 → E6
  • 压缩到底有没有用 → E7
  • 数字怎么如实说 → E8
过渡句：“先从最便宜、最确定的一层开始：把不变量写成测试。”

E1 · 不变量测试：把设计契约写成断言

痛点

  • 压缩逻辑被很多路径改写，改一处容易破坏另一处的隐含前提。
  • 隐含前提只存在于人的脑子里，换人就丢。

补丁

  • kernel 有自己的单元套件（kernel/tests/，约 94 个文件，涵盖 refs、tool-pairs、nudge、persist、terminal-escape 等），跑在 TS 源码上。
  • 宿主有集成套件（tests/，600 多个测试文件）；AGENTS.md 规定两层都绿才算完成。
  • 把规则编号写成测试：unified-acp-invariants.test.ts 里 I1–I4 四条硬规则——thinking 通道字节原样、模型 prose 可管理、写文件的 tool 参数字节原样、用户发的字节永不改写。
怎么说：我的做法是把“不能做什么”写成带编号的不变量，每条对应一个会真出事的后果：thinking 块有签名校验，改一个字节整个会话就废；tool 参数是用户意图，过滤了就悄悄损坏数据。这类规则靠 code review 守不住，必须变成会红的测试。代价是测试要跟着架构演进，所以我要求测试里写明规则出处和 issue 编号，将来想松动时能知道为什么当初这么定。
pi有 vitest 单元测试，另有独立的 packages/evals 做行为评估，二者分开。[代码]
codex以 Rust 集成测试为主，core/tests/suite 下约 240 个文件，用 mock 服务器喂 SSE 响应。[代码]
本项目kernel 与宿主两层套件；不变量带编号；宿主侧有 100 多个 issue*.test.ts，kernel 侧有 regression-*.test.ts，文件名即 issue/修复出处。[代码]
追问：为什么 kernel 要单独一套测试？

kernel 是纯函数库、可独立发布，且是 human-only 评审层。它的单测直接跑源码、不依赖宿主，能把“kernel 自身错了”和“宿主接错了”分开定位。宿主套件再作为集成层兜住接缝。[代码]

过渡句：“不变量守住了内部，但外部还有一个不受我控制的对手：上游 provider 的校验。”

E2 · 契约测试：把线上拒绝变成永久用例

痛点

  • 每家上游有自己的、文档不全的严格校验：Responses 的 item id 前缀、Anthropic 的 cache_control scope 顺序、thinking 模式要求回传 reasoning。
  • 这些只在生产里以 400 的形式暴露，修完很容易回归。

补丁

  • 校验对齐的 fake 上游：tests/wire-contract-fakes.ts 实现各 wire 最严格的已知校验；转发出去的 body 必须被它接受。
  • WIRE_RULES 账本：每条 WC-xxx 带规则摘要和出处（provenance），目前 18 个条目（含 1 条 header 级规则），编号 WC-001 到 WC-016，其中 WC-013、WC-016 各被两条规则共用；新增拒绝必须在修复 PR 里加条目+校验+用例。
  • golden 快照：tests/golden/wire-contract/ 保存所有工具 schema，按规范化 LF 文本逐字节比较；重新生成必须在 PR 里说明理由。
  • 四层：kernel 导出、bili 自己服务的面、插件 manifest、真实转发矩阵（脚本化客户端 → 代理 → fake 上游）。
怎么说：这里的原则是“账本只增不减”：每次线上被拒绝，不只是修，还要把约束本身编码进 fake 上游，这样之后任何改动再违反它都会红。账本的出处字段很关键——它记录“这条规则是从哪次事故学来的”，比如 WC-016（#2648）记录了一次真实的 400，还诚实写下了修复边界（只扫描 system 块、没覆盖 tools），因为没有流量证据就不扩大谓词。golden 的作用是让工具 schema 的任何漂移都显式可见，不能悄悄改。
pi没有对应的 provider 约束账本；兼容性由 provider 适配层和各 provider 的测试承担。[推断]
codex用 mock 服务器断言发出的请求形态，并有约 90 份 .snap 快照，把“请求上下文长什么样”做成可读快照。[代码]
本项目WIRE_RULES 账本 + 校验对齐 fake + golden；代理的转发形态是被测对象。[代码]
LangGraph框架层不负责 provider 线协议约束，这类契约测试需要自己做。[推断]
追问：golden 快照会不会变成“改了就重新生成”的橡皮图章？

会有这个风险，所以流程上加了人为摩擦：重新生成要运行专门脚本，PR 里必须写理由；账本和 kernel 的行为常量快照（kernel.json）都按“只增不减、需要说明”处理，并且 kernel 变更是 human-only 评审。这是靠流程而不是靠测试本身来防橡皮图章。[代码]

过渡句：“契约是点状的例子；对‘缓存永远不被打断’这种全称命题，例子再多也不够。”

E3 · prover、fuzz 与定理：对全称命题要更强的手段

痛点

  • “代理从不改写稳定字节”是一个全称命题，手写用例只能覆盖已想到的形状。
  • 缓存被打断的 bug 一个接一个：每次都是人工发现了矩阵里没有的形状。

补丁（强度递增）

  • 字节级 prover（cache-proof.test.ts）：捕获四种 wire 的真实出站 body，比较原始字节而不是 JSON 元素，覆盖增长、重试、模型切换（双探针 A/B）、宿主改写、折叠、压缩视图替换等场景；允许变化的字节必须被声明为 volatile carrier，其它任何差异都失败。
  • 属性式 fuzz（cache-seam-fuzz.test.ts）：生成会话形状而非枚举；默认 3 个场景、固定种子 1592，ACP_TEST_FUZZ=1 放宽到 12 个；失败会打印种子便于复现。
  • Z3 定理（cache-theorem.test.ts + proof/spec）：证明增长稳定性和 ref 单调；并故意做变异（改写稳定字节、归档后重置游标），要求求解器必须找到反例，证明定理不是空洞的。
怎么说：三者回答的是不同强度的问题。prover 把“没有打断缓存”变成会红的字节断言；fuzz 用生成代替枚举，找“矩阵里没有的形状”；定理则对契约本身做机器检查。我特别想强调两个诚实点：第一，定理证明的是装配契约，用 grounding 子测试把每条公理钉回真实代码，信任边界是写明的；第二，用变异测试确认证明不空洞——故意破坏一下，看检查器是否报警。另外 prover 里的 mock 上游兼做“理想前缀缓存计费裁判”，字节断言和计费命中率互相印证。
pi没看到字节级前缀稳定性的专门检查。[推断]
codex没看到对应的 fuzz/定理；快照测试在“给定输入看输出”的层面做回归。[推断]
本项目prover + fuzz + Z3 三层；无 z3 的机器上定理子测试单独跳过，CI 的 theorem lane 保证执行。[代码]
追问：形式化是不是过度工程？

要看代价收益。本项目的核心卖点是缓存稳定，一次打断是账单级后果，且历史上反复出现（测试注释里有一串 issue 编号）。所以对这一条投入定理级别是合理的；对别的部分（比如摘要写得好不好）形式化没有意义，那是统计问题。[推断]

过渡句：“这些都在我造的 mock 里。真实客户端有 UA、重试、wire 怪癖，mock 不到——需要真客户端。”

E4 · 真实客户端 e2e：mock 测不到的才值得花钱

痛点

  • 真实客户端的行为（UA、重试循环、对 id 的回放方式）在 mock 里复现不出来；很多回归就出在这里。
  • 但真模型 e2e 又贵又不稳定。

补丁：分层的 e2e

  • 真 codex + 真上游（e2e-codex.test.ts）：预热 → 负载增长 → ACP 压缩 → 纯度（压缩后召回早期事实，且不得回显埋入的污染值）→ 可选 forge。默认跳过，需 ACP_TEST_E2E=1，“never remove the gate”。
  • 确定性设计：负载增长靠客户端侧 seq 输出，不依赖模型配合；召回用哨兵数字，可程序判定。
  • 真客户端 + 假上游（e2e-codex-fake、native 系列）：零 token，进 CI。
  • hermetic 专项车道：图像计费（e2e-image-billing，无网络无 token，约 1 秒，永远跑）、本地 verdaccio 的自更新链、release canary。
怎么说：我的 e2e 策略是把不确定性挪出断言：让增长由客户端侧确定性地产生（模型常常把 seq 的输出缩短），让召回用哨兵值而不是让另一个模型判卷。真模型的套件默认关、只在改请求管线时手动跑；日常 CI 靠“真客户端+假上游”和 hermetic 车道获得大部分信心。release canary 值得一提：它对刚发布的同一份代码打两个版本号（N−1 和 N）推到本地 registry，只验证管道——版本发现、下载、原地切换——而不验证载荷质量，职责分得很清楚。
pievals 在 Docker 里跑真实 agent、真实模型，需要 PI_PROVIDER 和 PI_MODEL。[代码]
codex主要用 mock 服务器和 SSE 夹具做集成，不依赖真模型。[代码]
本项目三档：真模型（门控）、真客户端+假上游（CI）、hermetic（永远跑）。[代码]
追问：真模型 e2e 不稳定，断言失败了怎么办？

先判断是机制问题还是模型问题。设计上把断言放在可确定的量上（usage 先涨后跌、日志里出现拦截记录、哨兵召回），模型层面的随机性只影响“是否合作压缩”，所以允许“模型主动压”或“代理自主 preflight 压”两条路径任一发生。[代码]

过渡句：“测试越多越贵，下一个问题是：什么改动该跑哪些测试？”

E5 · CI 分层：按改动路径配置成本

痛点

  • 全跑太慢、太贵（含 Windows、多个 Node 版本）；但漏跑又会漏回归。
  • 流程性错误（改了 kernel 没升版本、release 提交夹带内容）靠人容易漏。

补丁

  • 第一层：秒级守卫（ci.yml）：version-guard、kernel-guard、pi-subagents-guard、lane-guard、docs-sync、docs-coverage、unused-exports、lock-sync（另有 config-surface-guard）；测试矩阵（ubuntu/windows × Node 22/24）needs 这些守卫，坏提交在第一层就停。
  • 第二层：按路径触发的专项车道：theorem lane 只在 src/loop/**、kernel/src/refs.ts 等相关路径变化时跑；各 native e2e、image、registry、canary 各有 workflow。
  • 自动合并门（AGENTS.md §7.4）：必须有复现原 bug 的回归测试、在 rebase 后的头上全绿，并且触及 wire/配置/kernel/updater 的一律人工评审。
怎么说：CI 的设计原则是“便宜的先、专用的按路径”。把流程规则（kernel 改动必须升版本、release 提交只改 version）也写成守卫，是因为这类错误人会漏，而漏了的后果是发布链坏掉。自动合并门里我最看重的一条是：必须有一个能复现原 bug 的回归测试——没有它，“修好了”只是声明。代价是 CI 配置本身也要维护，所以 docs-coverage、unused-exports 这类守卫也在保护它不腐烂。
pi评估是独立的 packages/evals，与单元测试分开命令运行。[代码]
codexRust workspace 的 CI 配置本章未逐行核对。[推断]
本项目守卫 → 平台矩阵 → 路径触发的专项车道；自动合并门明确排除高风险路径。[代码]
追问：为什么 e2e 里“真模型”不进默认 CI？

成本、稳定性和凭据三个原因；且它的价值在“改请求管线之前跑一遍”，不在每个提交都跑。AGENTS.md 规定改 src/server.ts、src/loop/** 等前至少跑 codex 套件的核心四阶段，改 updater 前跑 registry 套件——这是把昂贵测试绑到高风险改动，而非绑到每次提交。[代码]

过渡句：“前面评估的都是机制。但 agent 的好坏最终看任务做没做成——这涉及另一类评估：看结果还是看轨迹？”

E6 · 结果 vs 轨迹：agent 评估怎么选目标

痛点

  • 只看最终结果：模型走了弯路、重复读文件也算通过，且失败时不知道哪步错。
  • 只看轨迹（必须按某条路径调用某些工具）：会把合理的替代路径判错，评估变成对实现的耦合。

取舍

  • 结果为主，用可程序判定的哨兵：本项目 e2e 用哨兵数字和“不得回显污染值”判定，不让另一个模型判卷。
  • 轨迹只取机制性指标：re-fetch 次数、调用数、billed token——它们是压缩效果的代理量，不是对路径的硬编码要求。
  • LLM 当裁判要谨慎：位置/冗长偏好、自我偏好、同一模型评自己、判定不稳定；能用程序判的就别用模型判。
怎么说：我的原则是：终态正确是底线，轨迹只在它本身就是被测量时才看。对压缩系统，轨迹指标（重复读取次数、调用数）恰好就是效果，所以要看；但我不要求“必须先调用 A 再调用 B”。至于 LLM-as-judge，我只在无法程序化判定时用，并且会控制：固定判卷模型、盲评、校准一小批人工标注、多次取一致；否则判分噪声会淹没真实差异。本项目自己的 e2e 和试点探针尽量选了可程序判定的探针，我认为这是更稳的路线。
pi基于 vitest-evals：host eval 是普通断言套件；smoke.eval.ts 既断言输出，也断言 usage 与 token 数。[代码]
codex测试关注请求形态与事件序列（“这一轮发出了什么”），偏轨迹/形态断言。[推断]
本项目结果用哨兵判定；轨迹类量（re-fetch、billed token）只作为效果指标。[代码]
LangGraphLangSmith：离线评估（带参考的数据集，上线前）与在线评估（生产 trace，无参考）形成闭环；轨迹评估把实际步骤序列与期望对比，示例用 debug 流记录节点和工具调用；只按工具名匹配会忽略参数，文档建议用 LLM 评委看完整轨迹。[文档]
追问：轨迹评估什么时候是对的？

当路径本身有约束时：安全关键的工具顺序（先授权再执行）、必须经过某个检查点、或调用成本本身就是目标。否则它会把评估和实现绑死。折中是断言“不得发生什么”（负向约束），而不是“必须按这条路径”。[推断]

过渡句：“最后的问题：压缩到底有没有用？这就进入对照实验。”

E7 · A/B 评估：多臂对照与归因拆分

痛点

  • 生产里的省钱数字没有对照，无法分辨是压缩的功劳还是别的因素。
  • 不同工作负载下“最优压缩频率”不一样，单一场景的结论会误导。

论文里的受控试点（作者自报）[论文]

  • Session Marathon：18 个串行任务 × 6 遍 = 108 次任务执行，含从记忆回答的召回探针；窗口 65,536，单一评估模型，温度 0。
  • 四个臂：滑窗、阈值自动压缩（80%）、确定性引擎策略、billion-context。
  • 计费 token 相对保留基线降低 31–54%（默认配置 −31.5%，extreme 变体 −53.7%），re-fetch 降 63%（即 2.7×）；默认配置下召回探针无可测损失。
  • 归因拆分：“静止对照”（128K 窗口、单次运行 n=1）不执行任何压缩、只带 doctrine 文本和消息标签，就出现了 −62% 的 re-fetch 下降——所以 2.7× 归因于整套 doctrine+ref 标签+布局，而不是“任务条件压缩”本身。
  • 惰性基线：阈值臂在该规模下从未触发，行为等同滑窗，论文自己标为 artifact 而非对阈值方案的反驳。
怎么说：这一节我想展示的是怎么把一个好看的数字拆开。headline 是 2.7× 更少的重复读取，但作者自己做了一个静止对照，发现几乎不压缩也能得到同样的下降，所以结论应该是“doctrine 加标签的组合起作用”，而不是“压缩算法起作用”。同样，阈值基线没触发就是一个惰性基线，不能拿它当对手赢了的证据。这些是论文里自己写出来的，我只是复述；我自己做 A/B 也会先问：对照臂真的在工作吗？每个因素单独加是什么效果？此外探针有饱和（85–95%），“质量持平”受仪器灵敏度限制。
pidocs-lift eval：每个 case 在 without_docs 与 with_docs 两个隔离容器里各跑；成对比较，交替重复顺序以减少顺序偏差；某对缺失则不发布 headline lift，并标记 no-lift、对照饱和、flaky。[代码]
codex压缩相关测试验证机制（形态、恢复、分叉），不是对照式效果评估。[推断]
本项目试点多臂 + 静止对照 + 排列重跑；论文计划中的 oracle 臂与组件因子实验尚未完成。[论文] 证据强度的完整分级见第 3 章 K9，此处只讲评估方法。
Claude Code阈值自动压缩被论文作为“Claude Code 风格”的基线臂，是对其公开行为的模拟，而非直接使用该产品。[论文]
追问：如果你来设计一个更可信的压缩评估？

固定任务集和随机种子；对照臂必须真的触发并记录触发次数；因子化消融（doctrine、标签、压缩引擎各自独立开关）；多模型、多窗口；质量用可程序判定的回读探针，并加更难的探针避免饱和；报告均值加方差，不只报告单次。[推断]

追问：缓存命中率 94.2% 能算压缩的效果吗？

这是生产观察（单用户、08-20 快照，间隔不足 2 分钟的调用占约 89% 流量），且与“只追加”的结构性前提有关（论文称之为前提条件）。它说明机制没有破坏缓存，不能单独证明压缩带来收益；要证明收益必须有同工作负载的对照。[论文]

过渡句：“所有这些证据强度不同，最后一步是怎么如实地报告它。”

E8 · 证据分级：如实汇报强度

痛点

  • 把“机制已被证明”“受控试点”“生产观察”混在一起讲，会让听者高估整体结论。

我的分级

  1. 机制层，强：不变量、契约账本、字节 prover、定理（含变异检查）、真客户端 e2e——可复现、会在 CI 里红。[代码]
  2. 受控试点，中：31–54% 与 2.7×；单一模型、温度 0、少量种子/排列；归因已作拆分；仍属作者自报。[论文]
  3. 生产观察，弱于因果：约 70× 常驻折叠比、活跃节奏下 94.2% 缓存读；单一专家用户、无随机对照，反事实节省部分是建模的。[论文]
  4. 尚未验证：摘要质量量化、多模型、oracle 臂、组件因子实验。[论文]

如实写在文档里的东西

  • 账本记录修复边界（“没覆盖什么、为何不覆盖”）；
  • 文档与代码不一致时，以代码为准并说明（例见第 3 章 K9 的 merge-blocks）；
  • 数字带出处与适用口径。
怎么说：我会这样收尾：机制我有证据，效果我有试点，规模我只有观察。我不会把 70× 说成通用结论，也不会把 31–54% 说成对任何工作负载成立。面试里把“证据强度”讲清楚，比把数字讲漂亮更像专家：因为评估这件事本身的核心就是知道自己的结论能撑多重。

如果重做，改这四点

  1. 把对账成功率、回退次数做成一等可观测指标，并让 e2e 断言它。
  2. 补受控 A/B 的因子消融和多模型复现，把“作者自报”换成可复现脚本。
  3. 给摘要质量加回读探针，并加难度防饱和。
  4. 把 prover/fuzz 的 volatile carrier 声明与 golden 一起纳入同一份清单，减少隐含约定。[推断]
